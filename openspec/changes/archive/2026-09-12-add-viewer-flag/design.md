## Context

檢視器命令由 `resolveViewer` 從三個來源依序決定：`SPECTRA_VIEWER` 環境變數、外掛設定檔 `config.json` 的 `viewer` 欄位、內建預設 `less`。`EDITOR` 與 `PAGER` 刻意不列入來源，理由是它們與 git 等工具共用，在這裡挑檢視器會污染那些工具。設定檔那一層由 `readConfiguredViewer` 負責，只在 `HERDR_PLUGIN_CONFIG_DIR` 有值時才會去讀。

這個程式沒有命令列參數面。`process.argv` 在整個 src 目錄裡只出現在 entry-point 判斷，用來決定 `main()` 該不該跑；沒有任何旗標、沒有位置參數、沒有使用說明。Herdr 外掛 manifest 的 pane 命令是固定的兩個元素（node 與編譯後的 pane 入口），不會追加任何參數，所以本變更可以自由決定「多餘的參數」該怎麼處理，不會影響外掛路徑。

viewer 已能獨立執行，使用者手上就有一整行命令列可打，卻只能靠 export 一個名字裡帶 Herdr 的環境變數來換檢視器。

## Goals / Non-Goals

**Goals:**

- 讓檢視器可以在單次啟動時由命令列指定，不必動環境變數也不必建檔案。
- 給這個程式一個有使用說明、會拒絕打錯的參數面，而不是安靜忽略看不懂的參數。
- 把四層解析順序集中在一個函式裡，讓「哪個來源贏」這個問題在程式裡只有一個答案。
- 參數面在渲染前就結算完畢，`--help` 與 `--version` 在沒有終端機的管線裡也能用。

**Non-Goals:**

- 不把 `EDITOR` 或 `PAGER` 加回來源清單。原本排除它們的理由沒有改變。
- 不做互動式的檢視器選單，也不在 TUI 裡提供切換檢視器的按鍵。換檢視器是啟動時的決定。
- 不引入第三方命令列解析套件。現有執行期依賴只有 ink、react、yaml 三個，三個選項不值得再加一個。
- 不新增指定專案根目錄的參數。獨立執行時專案根目錄是當前工作目錄，這一點不在本變更範圍。
- 不動 Herdr 外掛路徑分割 pane 的行為，也不動兩個 adapter 的挑選規則。
- 不提供短別名。

## Decisions

### 只提供三個長格式選項，不提供短別名

參數面是 `--viewer <命令列>`、`--help`、`--version` 三個，都只有長格式，並且 `--viewer=<命令列>` 這種等號形式也接受。

不提供 `-h`、`-v` 之類的短別名，理由是 `-v` 在命令列世界裡同時是 version 與 verbose 的慣用縮寫，先把它綁給 version 會讓未來想加 `--verbose` 時沒有乾淨的短名可用；而三個選項的規模根本不需要縮寫來省打字。少了短別名也讓解析規則與 spec 的情境數量都小一圈。

等號形式要接受，是因為它是 `--viewer` 帶空白值時唯一不靠 shell 引號就能寫對的形式的替代寫法之一，而且使用者會反射性地這樣打；把它當成錯誤只會製造困惑。

### 旗標是第四個來源，四層順序集中在 resolveViewer

`resolveViewer` 的參數由兩個位置參數改為一個具名來源物件，欄位為 `flag`、`env`、`configured`，回傳仍是最終命令字串。旗標是最高優先來源，完整順序為：命令列旗標 → `SPECTRA_VIEWER` → 設定檔 `viewer` → `less`。每一層都先去除前後空白，取到非空字串就採用，否則往下一層。

改成具名物件而不是追加第三個位置參數，是為了避免「參數順序與優先順序不一致」這個陷阱：旗標優先度最高，但若追加在最後會變成第三個參數，讀程式的人很容易把位置當成優先序。具名欄位讓兩者脫鉤。

四層都留在同一個函式裡，而不是在呼叫點寫成「旗標有值就用旗標，否則呼叫 resolveViewer」。後者程式更短，但會讓 spec 裡那份有序來源清單在程式裡沒有單一對應處，未來要回答「誰贏」得看兩個地方。代價是既有兩支測試（pager 測試裡的兩個案例，以及 tui 目錄下依 spec 範例表逐列展開的表格測試）要改寫；因為來源表本來就要多一欄，這些測試無論如何都得改。

### 參數解析獨立成純函式模組

新增 `src/cli-args.ts`，匯出一個吃 `string[]`（即 `process.argv` 去掉前兩個元素）回傳結構化結果的純函式，不觸碰檔案系統、不讀環境變數、不印任何東西、不呼叫 `process.exit`。結果是一個帶標籤的聯集：照常執行（附帶解析出的檢視器與要印出的警告行）、印使用說明、印版本、參數錯誤（附帶錯誤訊息）四種。

使用說明文字也放這個模組，與解析規則同處一地，兩者一起改不容易走位。

印出、結束、決定狀態碼這些帶副作用的動作留在 `main()`。純函式加上呼叫點負責副作用，讓所有分支都能在沒有終端機、沒有子行程的情況下用普通單元測試蓋完。

### 取不到值的 --viewer 警告後跳過，不中止啟動

`--viewer` 沒有取到可用的值時——後面沒有任何元素、值是空字串、值只有空白——印一行警告到標準錯誤後把這個來源當成不存在，落到下一層，TUI 照常啟動。

這與設定檔既有的行為一致：一個存在但無法使用的 `config.json` 也是印一行警告後回退，不阻止 pane 啟動、不改變結束狀態碼。檢視器只在使用者按下開啟鍵時才用到，為一個可以回退的設定失敗擋掉整個瀏覽介面不成比例。

`--viewer` 出現多次時最後一次贏，這是命令列的通行慣例；但最後一次若取不到值，仍然照上述規則警告並回退，不會回頭採用前一次的值。

### 未知旗標與位置參數以使用說明拒絕並結束

任何無法辨識的旗標，以及任何位置參數，都是參數錯誤：印一行指出該參數、一行指向 `--help`，都到標準錯誤，以狀態碼 2 結束，TUI 不啟動。

安靜忽略是另一個選項，但這個程式不接受任何位置參數（專案根目錄取自當前工作目錄），所以一個看不懂的參數幾乎必然是打錯或誤解，忽略它會讓使用者以為設定生效了。

這個決定還順手處理了一個必然會發生的使用錯誤：帶旗標的檢視器命令必須整體加引號，`--viewer 'bat --style=plain'`。少了引號寫成 `--viewer bat --style=plain` 時，`--viewer` 只會吃到 `bat`，而 `--style=plain` 會變成無法辨識的旗標——於是使用者得到明確的錯誤訊息，而不是安靜地用了沒有旗標的 `bat`。使用說明裡要寫出這個引號規則。

狀態碼選 2 而非 1，是命令列工具區分「用法錯誤」與「執行失敗」的常見做法。

### --help 與 --version 在渲染前印出並結束

參數解析是 `main()` 的第一件事，排在讀取呼叫環境、解析專案根目錄、開啟滑鼠回報與渲染之前。`--help` 與 `--version` 因此完全不碰檔案系統掃描、不呼叫 Herdr、不開啟滑鼠回報、不進入 Ink，印完就以狀態碼 0 結束。

這讓兩者在沒有終端機的地方也能用——管線、CI、`npx spectra-viewer --version` 這種在腳本裡取版本的寫法——並且它們的驗證不需要偽終端機，普通測試就能蓋。

多個選項同時出現時的優先序是固定的：出現 `--help` 就印使用說明，否則出現 `--version` 就印版本，否則才判定參數錯誤。所以 `--help --bogus` 印的是使用說明而不是錯誤，符合使用者求助時的期待。

### --version 由套件的 package.json 讀取

版本字串在執行期從套件自己的 `package.json` 讀，位置以模組自身的 URL 為基準往上一層解析。編譯後的入口在 dist 目錄下，往上一層正好是套件根目錄；開發時直接跑編譯輸出、以及安裝到 node_modules 之後，這個相對位置都成立，因為 npm 一律會把 `package.json` 收進封裝檔。

不在建置時把版本字串寫進程式碼，因為那需要為一個選項多加一個產生程式碼的建置步驟，而套件版本本來就是唯一真相來源，多一份複本只會多一個走位的機會。

讀取失敗或 `version` 欄位不是字串時，印一行到標準錯誤並以狀態碼 1 結束。這裡不回退到「unknown」之類的占位字串：問到版本卻拿到假答案比拿到錯誤更糟。讀取函式接受注入的讀檔函式，所以失敗分支可以測。

## Implementation Contract

**Behavior**

- 啟動時帶 `--viewer <命令列>` 或 `--viewer=<命令列>`，該值成為檢視器命令，覆蓋 `SPECTRA_VIEWER` 與設定檔。按下開啟鍵時狀態列顯示 `Opened in <該命令列>`，兩條檢視器路徑（Herdr 分割 pane 與獨立執行接管終端機）都適用。
- 值當成一整行命令列處理：以空白切割，artifact 的絕對路徑附加為最後一個獨立元素。帶旗標的命令必須整體加引號。
- `--help` 印使用說明到標準輸出後以 0 結束。`--version` 印版本字串到標準輸出後以 0 結束。兩者都不進入 TUI。
- 無法辨識的旗標或任何位置參數，印錯誤與指引到標準錯誤後以 2 結束，TUI 不啟動。
- `--viewer` 取不到可用值時，印一行警告到標準錯誤，該來源視為不存在，TUI 照常啟動並使用下一層來源。

**Interface / data shape**

- 新模組 `src/cli-args.ts` 匯出：
  - 解析函式：吃 `string[]`（`process.argv` 去掉前兩個元素），回傳帶標籤聯集，四個變體對應照常執行、印使用說明、印版本、參數錯誤。照常執行的變體帶兩個欄位：解析出的檢視器命令（字串，或無旗標與旗標無效時為 null）與要印出的警告行陣列。參數錯誤的變體帶錯誤訊息。
  - 使用說明常數字串：含用法一行、三個選項各一行、四層來源順序、以及帶旗標命令要加引號的說明。
  - 版本讀取函式：接受注入的讀檔函式，預設為同步讀檔；回傳版本字串，讀不到或欄位不是字串時擲出。
- `resolveViewer` 的簽章改為單一具名來源物件，欄位 `flag`、`env`、`configured`，回傳最終命令字串。`env` 為必填，另兩個可省略。

**Failure modes**

- 參數錯誤：標準錯誤兩行，狀態碼 2，不啟動 TUI。
- 版本讀取失敗：標準錯誤一行，狀態碼 1。
- `--viewer` 無有效值：標準錯誤一行警告，回退到下一層來源，狀態碼不受影響，TUI 照常啟動。
- 既有的設定檔失敗行為不變：一行警告後回退，不影響啟動與狀態碼。

**Acceptance criteria**

- `src/cli-args.ts` 的解析函式有單元測試，涵蓋：空參數列、`--viewer` 空白分隔形式、等號形式、值前後帶空白、`--viewer` 後面沒有元素、值為空字串、值只有空白、`--viewer` 重複出現、未知旗標、位置參數、`--help`、`--version`、`--help` 與 `--version` 同時出現、`--help` 與未知旗標同時出現。
- `resolveViewer` 的表格測試依 spec 的來源順序範例表逐列展開，每列一個案例。
- 版本讀取函式有測試涵蓋成功、檔案讀取擲錯、`version` 欄位不是字串三種情形。
- 以編譯輸出實測四條命令並貼出輸出：`--help`（狀態碼 0、印出使用說明）、`--version`（狀態碼 0、印出與 `package.json` 相同的版本）、一個未知旗標（狀態碼 2、錯誤訊息含該旗標）、`--viewer` 後面沒有值（印出警告且不是以 2 結束）。前三條可在管線中執行，不需要偽終端機。
- 帶 `--viewer` 啟動並按開啟鍵，狀態列顯示 `Opened in <該命令列>`；這一項需要偽終端機，以手動驗證方式記錄實際輸出。
- 既有測試全數通過，`npm run typecheck` 無錯誤。

**Scope boundaries**

- 在範圍內：新增參數解析模組與其測試；`resolveViewer` 簽章與四層順序；`main()` 於最前面結算參數面；兩支既有測試隨簽章改寫；README 檢視器設定一節補上獨立執行說明與新旗標；`changes-pane` 與 `standalone-cli` 兩份 delta spec。
- 不在範圍內：Herdr 外掛 manifest（pane 命令不需要改）；兩個 adapter 的挑選規則與 `src/pager.ts` 的終端機交接；`src/config.ts` 的設定檔讀取行為；`src/tui/` 底下任何元件；`src/open.ts`。

## Risks / Trade-offs

- 拒絕位置參數會讓 `npx spectra-viewer .` 這種直覺寫法報錯 → 錯誤訊息指向 `--help`，而使用說明第一行就寫明本程式不接受位置參數、專案根目錄取自當前工作目錄。比起安靜忽略一個使用者以為有作用的參數，明確報錯更好。
- `resolveViewer` 簽章改變會動到兩支既有測試 → 兩支測試都是這份程式庫自己的，且來源範例表本來就要加一欄，改寫是必然成本而非額外成本。
- 帶旗標的檢視器命令少加引號時，`--style=plain` 之類的殘餘會被當成未知旗標，錯誤訊息指的是殘餘旗標而不是根本原因 → 使用說明裡明確寫出引號規則，並在未知旗標的錯誤訊息後保留指向 `--help` 的那一行，使用者看了說明就會發現引號問題。
- 執行期讀 `package.json` 取版本，多了一個檔案系統依賴 → 只在 `--version` 這條路徑上發生，其他啟動路徑完全不讀；讀不到時明確報錯而非給出假版本。
